## Problem Statement

"카더라 말고"는 건강, 육아, 교육, 운동, 영양, 심리처럼 생활 의사결정에 영향을 주는 주장에 대해 실제 연구 문헌을 찾아 한국어로 검증해 주는 MCP 서버다.

사용자는 "이거 진짜 맞아?"라고 묻는다. 서버는 검색 결과 목록을 던지지 않고, 실제 API에서 찾은 연구만 근거로 삼아 결론, 근거 수준, 출처, 주의 문구를 반환한다.

공모전 맥락은 AGENTIC PLAYER 10 출품이다. 예선은 안정성, 편의성, 창의성이 중요하고, 본선은 Kakao Tools 사용자 투표가 붙으므로 대중이 바로 이해하는 답변 품질이 중요하다.

## What Makes This Cool

핵심 재미는 "AI가 말해주는 것"이 아니라 "AI가 진짜 논문을 찾아와서 카더라를 정리해 주는 것"이다. 일반 사용자가 논문 검색, 영어 초록 해석, 근거 수준 판단을 직접 하지 않아도 된다.

가장 보여주기 좋은 데모는 다음 흐름이다.

1. 사용자가 생활 질문을 입력한다: "공복 유산소가 살 더 잘 빠져?"
2. 서버가 카테고리를 분류한다: 운동/영양.
3. 서버가 영어 검색어를 만든다.
4. PubMed와 Semantic Scholar에서 실제 논문을 찾는다.
5. 답변은 "결론부터", "근거는", "주의할 점", "출처" 순서로 한국어로 나온다.
6. 같은 주제를 다시 물으면 캐시에서 빠르게 답한다.

## Constraints

- 절대 없는 논문을 인용하지 않는다. API 검색 결과에 없는 연구는 답변에 들어갈 수 없다.
- 진단, 처방, 복용 지시는 하지 않는다. 연구 정보 제공과 전문가 상담 권유로 범위를 제한한다.
- 개인정보는 저장하지 않는다. 질문 주제의 익명 집계와 캐시만 저장한다.
- MVP는 출품 마감 전 완성도를 우선한다. 모든 API를 붙이기보다 PubMed, Semantic Scholar, 캐시, 안전장치를 먼저 완성한다.
- 응답 형식은 실제 샘플 답변을 뽑은 뒤 다듬는다. 다만 구조는 결론, 근거, 한계, 출처, 안전 문구를 기본으로 둔다.

## Premises

1. 사용자가 원하는 것은 "논문 검색"이 아니라 "내 질문에 대한 근거 있는 판단"이다.
2. 출품 MVP에서는 카테고리 2-3개만 잘 되는 것이 전 분야 얕은 지원보다 낫다.
3. 환각 차단은 기능이 아니라 생명선이다. 검색 실패 시 정직하게 실패를 반환해야 한다.
4. 캐시는 속도 최적화뿐 아니라 제품 자산이다. 반복 질문이 곧 인기 카더라 데이터가 된다.
5. PlayMCP 심사와 본선 투표에서는 답변의 신뢰감과 이해 가능성이 API 개수보다 중요하다.

## Approaches Considered

### Approach A: 출품 MVP

Summary: PubMed와 Semantic Scholar만 먼저 붙이고, SQLite 기반 캐시와 간단한 근거 등급 로직으로 MCP 도구 2-3개를 만든다.

Effort: M

Risk: Low-Med

Pros:

- 출품 마감 전에 실제 동작하는 서버를 만들 가능성이 가장 높다.
- 환각 차단, 출처 표기, 의료 경계 문구 같은 핵심 신뢰 요소를 먼저 검증할 수 있다.
- 카테고리별 검색어 변환과 응답 형식을 빠르게 샘플링할 수 있다.

Cons:

- Cochrane, WHO, OpenAlex까지 붙인 버전보다 근거 등급이 단순하다.
- 교육/심리처럼 PubMed 커버리지가 약한 분야는 초반 답변 품질이 불균등할 수 있다.
- 한국 논문 보강은 후순위가 된다.

Reuses: 새 저장소라 재사용할 코드가 없다. 단, MCP 서버 표준 구조와 SQLite 캐시를 얇게 둬서 다음 확장이 쉽도록 만든다.

### Approach B: 이상적인 연구 검증 엔진

Summary: PubMed, Semantic Scholar, OpenAlex, Cochrane, WHO/MyHealthfinder, ERIC까지 소스 레이어를 만들고, 근거 등급, 다중 카테고리, 임베딩 검색까지 포함한다.

Effort: XL

Risk: High

Pros:

- 기획서의 장기 비전에 가장 가깝다.
- 근거 등급과 카테고리 확장성이 좋아 본선 이후 서비스로 키우기 쉽다.
- 반복 질문 데이터와 RAG 구조가 제대로 쌓인다.

Cons:

- 출품 전 안정화가 어려울 수 있다.
- API별 응답 포맷, rate limit, 오류 처리 범위가 커진다.
- 답변 품질보다 파이프라인 복잡도에 시간을 빼앗길 위험이 있다.

Reuses: Approach A의 검색, 캐시, citation 모델을 확장한다.

### Approach C: 데모 우선 검증기

Summary: 실시간 검색 범위를 더 줄이고, 인기 질문 20-30개에 대해 사전 검증 캐시를 만들어 데모 성공률을 극대화한다.

Effort: S-M

Risk: Med

Pros:

- 심사 데모에서 빠르고 안정적이다.
- 답변 톤과 UX를 충분히 다듬을 수 있다.
- 본선 투표용 "이번 달 많이 검증한 카더라" 기능까지 빨리 보여줄 수 있다.

Cons:

- 사용자가 예측 밖 질문을 하면 품질이 떨어진다.
- "무엇이든 검증"이라는 약속과 실제 MVP 사이 간극이 생긴다.
- MCP의 외부 API 호출 본질이 약해 보일 수 있다.

Reuses: Approach A의 캐시 구조를 먼저 채운 형태로 쓴다.

## Recommended Approach

Approach A를 추천한다. 이 프로젝트의 첫 목표는 공모전 출품 가능한 MCP 서버이므로, "실제로 검색하고, 실제 출처만 인용하고, 한국어로 신뢰감 있게 답한다"를 끝까지 닫는 것이 가장 중요하다.

초기 구현은 Approach A에서 시작했지만, 기획서 4장의 데이터 소스 요구에 맞춰 PubMed, Semantic Scholar, OpenAlex, Europe PMC, Crossref, ERIC, MyHealthfinder, arXiv, bioRxiv/medRxiv, CORE adapter까지 확장한다. WHO GHO, CDC, KCI, RISS는 논문 검색과 데이터 모델이 다르거나 키/공식 endpoint 확인이 필요하므로 별도 단계로 둔다.

## MVP Tool Surface

### `check_claim`

사용자의 카더라 질문을 검증한다.

Input:

- `question`: 한국어 자연어 질문.
- `category`: optional. `health`, `childcare`, `education`, `exercise`, `nutrition`, `psychology`, `auto`.
- `audience`: optional. 기본값 `general`.

Output:

- `answer_ko`: 한국어 답변.
- `verdict`: `supported`, `mixed`, `not_supported`, `insufficient_evidence`, `safety_redirect`.
- `evidence_level`: `systematic_review`, `clinical_study`, `observational_study`, `preprint`, `official_guidance`, `unknown`.
- `citations`: 제목, 저자, 연도, DOI/URL, source API.
- `limitations`: 연구 한계와 답변 신뢰도.
- `safety_note`: 의료/전문가 상담 안내.
- `cached`: boolean.

### `find_evidence`

답변 생성 없이 관련 연구만 구조화해서 반환한다. 디버깅과 투명성용이다.

Input:

- `question`
- `category`
- `limit`

Output:

- `query_terms`
- `papers`
- `source_errors`

### `popular_claims`

익명 집계 기반 인기 검증 주제를 반환한다.

Input:

- `category`
- `period`: `7d`, `30d`, `all`

Output:

- `claims`
- `count`
- `last_checked_at`

### `data_sources`

기획서 4장의 API별 구현 여부, 활성 여부, 키 필요 여부, 신청/문서 링크를 반환한다.

## Pipeline

1. Normalize question.
2. Classify category.
3. Check cache.
4. If cache miss or expired, translate question into English research query terms.
5. Search PubMed.
6. Search Semantic Scholar.
7. Merge and dedupe by DOI/title.
8. Rank by evidence level, recency, citation count when available, and source reliability.
9. If no acceptable evidence exists, return `insufficient_evidence`.
10. Generate Korean answer from retrieved evidence only.
11. Persist temporary cache.
12. On repeated topic, promote cache and store richer metadata.

## Safety Behavior

- Emergency or severe symptom patterns return `safety_redirect` and do not perform normal answer generation.
- Medication combination, dosage, pregnancy, infant emergency, acute symptoms, self-harm, and severe mental health claims get stricter warnings.
- Every answer includes a short "연구 정보 제공이며 진단/처방이 아니다" note.
- If API results are weak, the answer says so directly.

## Success Criteria

- `check_claim` returns an answer with at least one real citation for common MVP questions.
- No citation appears unless it came from PubMed or Semantic Scholar response data.
- A no-result query returns `insufficient_evidence`, not a fabricated answer.
- Repeating a question hits cache.
- Sensitive medical questions avoid diagnosis and prescription language.
- PlayMCP registration flow has a deployed endpoint, not just local code.
- Demo has 10 representative questions that complete reliably.

## Distribution Plan

The deliverable is a hosted MCP server for PlayMCP.

Implementation target:

- Runtime: Node.js/TypeScript unless the eventual PlayMCP/Kakao Cloud template strongly favors another runtime.
- Transport: MCP server exposed behind the endpoint required by PlayMCP.
- Storage: SQLite for MVP if deployment allows persistent disk; otherwise managed Postgres or hosted key-value store.
- Deployment: Kakao Cloud endpoint for contest registration.
- CI: run typecheck, lint, unit tests, and integration tests against mocked APIs before deploy.

## What I Noticed

- The original plan correctly rejects "논문 검색기" as the product category. The stronger framing is "일반인용 카더라 검증기".
- The plan already identifies the hardest product risk: trust. That means implementation should spend early time on citation integrity, not on adding more APIs.
- The broad target "전 국민" is acceptable for a public vote, but the MVP should still start with 2-3 categories so quality is obvious.
- The cache idea is not just optimization. It is the bridge from demo to product: repeated claims become trend data.
